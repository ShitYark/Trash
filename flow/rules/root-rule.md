# Main

1. **Сборка и тесты — только через `make`** (`make build` / `make test` / `make run`): обёртки держат единый DerivedData и пишут полный лог в файл. Голый `xcodebuild` — только для интроспекции (`-list`, `-showBuildSettings`, `-version`); остальное блокирует guard-хук. Текстовый поиск по коду веди обычными Grep/rg
2. **Безопасность удаления.** Агент не удаляет файлы пользователя вне проекта — ни командой, ни запуском очистки в приложении:
   - логику удаления проверяй тестами во временной папке (`FileManager.default.temporaryDirectory`), не на реальном `~`;
   - в запущенном приложении кнопку «Очистить» не нажимай — сканирование только читает диск, его запускать можно;
   - `rm` и `find -delete` за пределами проекта блокирует guard-хук; обход `FLOW_ALLOW_RM=1` — только по явной просьбе пользователя в чате
3. Относись к задаче критически: покажи интерпретацию запроса; если она добавляет предположения или выбор между вариантами — дождись подтверждения, прежде чем действовать; тривиально совпадает с запросом — продолжай без остановки
4. Для длинных и многоэтапных задач сохраняй план и прогресс в `flow/plans/`
5. Документация в `flow/knowledge/**` и глоссарий `flow/rules/glossary.md` поддерживаются инкрементально в рамках команд `/dev:*`. Каждая задача затрагивает документацию своего модуля: `/dev:code` дополняет или создаёт её, `/dev:search`, `/dev:review` и `/dev:analyze` фиксируют gap и предлагают закрыть через `/dev:code`. Отдельного ручного прохода по всему проекту не требуется
6. Все временные файлы агента (рабочие TSV, JSON, ad-hoc скрипты, промежуточные дампы) — только в `tmp/<topic>/`, никогда в `/tmp` или других папках вне проекта. Единственное исключение — системный scratchpad Claude (`/tmp/claude*`). Подробности — `flow/meta/conventions.md` → «Временные файлы агента»
7. Ошибку сборки, причина которой **не выводится из её текста** (Swift 6 concurrency, тулчейн, специфика нашей сборки), после фикса зафиксируй в gotchas-доке `flow/knowledge/engineering/<слой>-gotchas.md`. Тривиальное (опечатка, забытый импорт, очевидный фикс из текста ошибки) не записывай; частный пример уже описанного правила — строка-пример, а не новая запись. Критерий и формат — `flow/meta/conventions.md` → «Правила для gotchas-документов»
8. Всегда следуй принципам **DRY, KISS, YAGNI**: не дублируй, делай проще, не реализуй про запас
9. **Код из другой ветки — без переключения рабочего дерева:** `git show|log|blame <ветка> -- <путь>`. Рабочую ветку (`git checkout`/`switch`) не переключай — это сбивает работу пользователя
10. **Формат ответов** — по [`flow/rules/response-format.md`](response-format.md): итог первой строкой, секции `###` со статус-маркерами ✅/⚠️/❌, абзац не длиннее 3 строк, перечисления — списком или таблицей, не прозой, без вложенных скобок
11. **Fan-out субагентов — не больше ~10 параллельных.** Широкие веера субагентов и Workflow-оркестрацию не запускай по собственной инициативе — только по явной просьбе пользователя. Нужно больше ~10 — остановись и согласуй разбиение
12. **Не выдумывай факты.** Любое фактическое утверждение — только после проверки: grep, чтение файла, фактический прогон команды; не по памяти и не по аналогии. Нечем проверить — так и скажи («не могу проверить, потому что …»), вместо «должно быть так». Типовые классы утверждений и способы их проверить — [`flow/knowledge/engineering/never-fabricate-verify-first.md`](../knowledge/engineering/never-fabricate-verify-first.md)

# Before Work

1. Начни с глоссария `flow/rules/glossary.md` — поиском, не чтением: `grep -n -i -E` по корням слов задачи и их синонимам. Пусто — второй поиск другими словами и поиск по `flow/knowledge/`: длинные формулировки и симптомы живут в документах. Не помогло — `Read` глоссария целиком
2. Через глоссарий и контекст задачи определи, какие документы действительно нужны
3. Подробные документы из `flow/knowledge/**` читай только по необходимости
4. Если непонятно, где искать код или затронуто несколько слоёв, используй `flow/project-map.md` как вспомогательную карту
5. После реализации оцени качество результата и при необходимости предложи улучшения
6. В конце любой задачи проверь документацию затронутого модуля в `flow/knowledge/**`: дополни в `/dev:code`, зафиксируй gap в `/dev:search`, `/dev:review` и `/dev:analyze`
