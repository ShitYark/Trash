# Соглашения формата

Эти правила применяются к документам `flow/**`, `.claude/commands/**` и `.claude/agents/**`.

## Общие правила

- Язык: русский
- Имена файлов: kebab-case, латиница (`build-and-test.md`)
- Расширение документов: `.md`
- Кодировка: UTF-8

## Архитектура команд

- Источник логики команд — `.claude/commands/dev/` и `.claude/agents/`. Других слоёв нет: команды самодостаточны, агента не отправляют прыгать между слоями.
- Команды для других агентов (Codex, Cursor и т.п.) не заводятся без согласованного meta-плана. `AGENTS.md` другие агенты могут читать нативно.
- Под-рутины (`artifacts`) вызываются из основных команд как шаги, а не как самостоятельный пользовательский вход.

## Структура документа модуля (`flow/knowledge/modules/*.md`)

Модуль — функциональная часть приложения со своей логикой и своими файлами. Минимально:

1. Заголовок модуля и краткое описание (1–3 предложения)
2. Точки входа: типы и методы с путями
3. Связанные модули
4. Ключевые сценарии и потоки
5. Нюансы и подводные камни
6. `## Кодовые якоря (индекс)` — второстепенные кодовые имена (строка «Код») и длинные формулировки поиска (строка «Формулировки поиска»)
7. `### Ключевые файлы` — обязательна

Инженерные документы без модуля (сборка, стиль, gotchas) — в `flow/knowledge/engineering/`.

### Секция «Ключевые файлы»

Источник истины для карты `flow/meta/code-to-module-map.json` и для `/dev:history`. Формат — плоский список путей от корня репо, один путь — одна строка:

```markdown
### Ключевые файлы

- /Trash/Services/<File>.swift (service — <область>)
- /Trash/Views/<Folder>/ (директория — <область>)
```

- **Директория** — путь заканчивается на `/`.
- **Файл** — путь с расширением.
- **Комментарий в скобках** — `(<тип> — <область>)`; часть после ` — ` — имя области для группировки записей в истории модуля.
- Подзаголовков внутри секции нет — это ломает плоский парсинг.
- Новый ключевой файл модуля → строка здесь и правило в карте. Это часть `/dev:code` Шаг 9.

## Правила для глоссария (`flow/rules/glossary.md`)

- Один файл, одна таблица из **двух колонок**: «Слова-триггеры» (термины, синонимы, имена типов — всё, по чему ищут) → «Куда идти» (первый путь — основной документ, обязательный к прочтению; дальше через `;` — смежные с короткой пометкой «когда»).
- **Строка = один целевой документ.** Все слова, ведущие в документ, собраны в одной строке.
- **Кодовые якоря — в доке модуля, не в глоссарии.** Имена методов и свойств живут в `## Кодовые якоря (индекс)` дока: они меняются при рефакторинге. В глоссарии — имена сущностей и главные типы.
- **Пути — относительно `flow/knowledge/`**; путь без каталога — `modules/`; пути с другим корнем (`flow/…`, `.claude/…`, `Trash/…`) — полностью.
- **Ссылки на `flow/history/**` в глоссарий не добавляются никогда**: история изолирована от навигации, с ней работают субагенты.

### Что попадает в «Слова-триггеры»

Только то, по чему **реально ищут** и что нельзя найти через уже стоящее в строке слово. Не добавляй:

- производное от слова, уже стоящего в строке;
- описательную фразу или визуальную деталь;
- повтор имени типа, уже названного в строке;
- описание ситуации, уместное в задаче про любой модуль — триггер обязан вести в один документ;
- имена методов и свойств — им место в «Кодовых якорях».

**Оформление:** в первой колонке нет кавычек, бэктиков, пояснений в скобках и жирного; во второй бэктики отделяют пути, названий разделов и знака § нет — раздел агент находит по оглавлению документа.

**Длина ячейки:** цель — триггеры до 250 символов, «Куда идти» до 150; предел — 400 и 300. Размер файла: больше 40 000 байт — предупреждение, больше 60 000 — ошибка (перестаёт помещаться в один `Read`). Всё это проверяет `check-glossary.py`; на Stop-хуке нарушение в изменённой строке блокирует завершение.

## Правила для gotchas-документов (`flow/knowledge/engineering/*-gotchas.md`)

Назначение — сократить итерации сборки и отладки на ошибках, которые **невозможно предсказать из кода**. Это не журнал всех ошибок. Файл заводится при первом случае и регистрируется строкой в глоссарии.

Записывай, только если выполнены **все три** условия:

1. Причина не выводится из текста ошибки.
2. Специфика проекта или тулчейна: Swift 6 concurrency, синхронизируемые папки, подпись, TCC — а не общее знание языка.
3. Класс ошибки может повториться.

Формат:

- **Индекс симптомов вверху файла** — таблица «текст ошибки / симптом → правило или запись».
- **Правила** — обобщённые паттерны с примерами.
- **Записи-случаи** — 5–8 строк: `#### <дата> — <симптом одной фразой>` + Симптом / Причина / Правильно / Урок.
- Перед новой записью — grep: не частный ли это пример существующего правила. Если да — строка-пример к правилу, а не новая запись.
- При росте до ~25 КБ — консолидация: частные случаи схлопнуть в правила, устаревшее удалить.

## Проверка правок инструкций — симуляцией

Правка команд, глоссария или правил считается проверенной не после чтения диффа, а после **прогона**: субагент получает реалистичную задачу и работает по новой редакции файлов; в финале возвращает трассу — какие файлы открывал и почему. Дешёвая альтернатива для мелких правок — самопроверка «воспринял бы я эту формулировку как обязательную, читая её впервые».

## Правила для планов

### Планы задач (`flow/plans/*.md`)

- Имя файла: `<module>-<slug>.md`, slug — kebab-case по сути задачи: `cleanup-large-files.md`. Задача на несколько модулей — по главному модулю.
- Формат свободный: заголовок, `## Метаданные` (дата, модуль, статус), DoD, этапы, решения, прогресс.
- План — рабочий документ задачи. Устоявшееся знание из него после задачи переносится в док модуля, хроника — в историю модуля.

### Планы улучшений flow (`flow/meta/plans/*.md`)

YAML frontmatter обязателен:

```
---
title: Краткое название плана
status: proposed | approved | in_progress | done | rejected | on_hold
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

Тело: Проблема → Почему важно → Предлагаемое решение → Риски → Критерии готовности → Открытые вопросы. Workflow статусов и индекс — `flow/meta/plans/README.md`.

## Правила для feedback-log

Файл `flow/meta/feedback-log.md` — журнал отклонений агента от flow.

- Запись = один разовый косяк или повторяющийся паттерн.
- Поля: контекст, что пошло не так, гипотеза причины, возможное улучшение.
- Пишет агент — с подтверждения пользователя или по его просьбе.
- Активные и разобранные записи — в одном файле, в разных секциях.
- При 5+ активных записях агент напоминает разобрать журнал. Разбор превращает запись в план `flow/meta/plans/` или отбрасывает её с причиной.

## Граница между memory и `flow/rules/`

- **`flow/rules/`** — правила для любого агента, работающего с этим проектом: код, термины, процесс, инструменты.
- **memory** — личные предпочтения пользователя, применимые ко всем его проектам и не привязанные к коду.
- Новый feedback: «правило про проект» → `flow/rules/` или `flow/knowledge/`; «про человека» → memory. При конфликте для проектной работы побеждает `flow/rules/`.
- TODO по задаче — не memory и не rules: `flow/plans/` или `feedback-log.md`.

## Стиль текста

- Короткие предложения, маркированные списки, минимум воды, сразу к сути.
- Никаких эмодзи в документах `flow/knowledge/**` и `flow/meta/**`. Статус-маркеры ✅/⚠️/❌ — только в ответах агента и шаблонах отчётов команд.

## Чек-перед-коммитом

- В документе нет дубликатов с другими файлами `.claude/` / `flow/`.
- Все ссылки рабочие: `make flow-check`.
- Пути и имена кода в документе актуальны.
- Frontmatter планов flow валиден, `updated` обновлено.

## Временные файлы агента — `tmp/`

Все временные файлы агента — рабочие TSV/JSON, ad-hoc скрипты, промежуточные выводы — только в `tmp/<topic>/`. Никогда в `/tmp` или других папках вне проекта; единственное исключение — системный scratchpad Claude (`/tmp/claude*`).

- **Подпапка по теме задачи**: `tmp/cleanup-history/`, `tmp/large-files/`.
- **gitignore:** `tmp/*` + `!tmp/.gitkeep`.
- **Очистка — на пользователе.** Команды `/dev:*` её не предлагают и не выполняют.
- **Многоразовый скрипт — не в tmp.** Начал использоваться повторно — переносится в `flow/scripts/` и параметризуется.

## Debug-артефакты — `Debug/`

Папка `Debug/` в корне, в `.gitignore`. Сюда пользователь кладёт артефакты для разбора: краш-репорты, логи, скриншоты, листинги папок. Работа с ними — `/dev:artifacts`. Очистка — на пользователе.

## Хуки Claude Code

Хуки заведены в `.claude/settings.json`: Stop — `check-doc-sync`, `check-links`, `check-glossary`, `check-sizes`; PreToolUse (matcher `Bash`) — `guard-bash`.

- **Скрипт хука адресуется от корня проекта, не от cwd:** `python3 "${CLAUDE_PROJECT_DIR}/flow/scripts/<скрипт>.py"`. Хук стартует в cwd агента; путь от cwd из подкаталога не находится, `python3` выходит с кодом 2, а для PreToolUse это «заблокировать».
- **Корень скрипт находит сам — от своего расположения** (`__file__`), git зовёт с явным корнем `git -C <корень>`.
- **guard-bash:** каждое правило — узкий паттерн плюс флаг обхода `FLOW_ALLOW_*=1` в самой команде; флаг ставится только по явной просьбе пользователя. Ошибка самого хука — пропуск: guard не должен ронять легитимную работу.
- Тесты: `make flow-test` — guard-правила, резолвер карты, линтер глоссария и запуск команд хуков из подкаталога и из папки вне git.

## Doc-sync hook

В конце сессии `check-doc-sync.py` сопоставляет незакоммиченные файлы кода с картой `flow/meta/code-to-module-map.json` и напоминает, если затронут модуль, чей документ `flow/knowledge/modules/<module>.md` не обновлён.

- Правка не требует документации (рефакторинг, форматирование) — пометка `[skip-doc-check]` в сообщении коммита. Скрипт читает сообщение **HEAD-коммита**, а дифф берёт **незакоммиченный**: маркер подействует на следующую сессию, не на текущую.
- `paths` разрешается по **самому длинному совпадению префикса**; ключ — директория (`/` в конце) или точный путь файла. `non_modules` участвует в том же сравнении и даёт «файл вне модулей».
- `name_prefixes` — независимая ось: файлы одного модуля, разбросанные по разным папкам.
- Один файл → один модуль по пути. Два модуля на один файл — коллизия правил: заведи частное правило.
- Источник истины при заведении правила — секция `### Ключевые файлы` документа модуля.

## Формат записи истории модуля

Файлы `flow/history/<module>-history.md` — хроника правок модуля. Дополняют `<module>.md`: док описывает, **как модуль работает сейчас**, история — **что и почему менялось**, включая осознанные решения, которые не надо «чинить».

### Структура файла

- Заголовок `# История изменений: <module>` + одна строка описания со ссылкой на док модуля
- `## Активные записи` — записи по дате, новые сверху; при росте — подсекции по областям `### <область>` из комментариев «Ключевых файлов»
- `## Архив` — однострочные дайджесты архивных периодов (появляется после первой архивации)

### Формат одной записи

```
#### YYYY-MM-DD — <сообщение коммита>

- Суть: <1–3 предложения: что изменилось и зачем>
```

Заголовок записи **дословно совпадает с сообщением коммита** (`flow/rules/naming-conventions.md`): ключей задач нет, связь «запись ↔ коммит» держится на тексте — `git log --grep "<заголовок>"`.

Дополнительные поля:

- `Решения:` — осознанные решения задачи, которые выглядят как баг или ограничение. Слово **«намеренно»** — сигнал для субагента `context`: такое поведение не «чинится» без арбитража пользователя.
- `Тесты:` — что покрыто
- `Файлы:` — затронутые файлы
- `План:` — `flow/plans/<plan>.md`, если был

Длина записи — до ~3 КБ: хроника, а не пересказ диффа.

### Кто и когда обновляет

- **Текущие обновления** — `/dev:code` Шаг 9, если задача меняла код модуля.
- **Генерация с нуля и архивация** — `/dev:history <module>`.
- Исследовательские задачи без правок кода в историю не пишутся.

## Расслоённый документ модуля

Когда док модуля перерастает читаемость, применяется progressive disclosure: хаб `<module>.md` + под-файлы `<module>/<intent>.md`.

- Признак — рядом с `<module>.md` есть каталог `<module>/`.
- Хаб на прежнем пути: описание, индекс под-файлов (`[<file>.md](<module>/<file>.md) — что внутри и когда читать (N КБ)`), «Кодовые якоря», `### Ключевые файлы`. Контент в хаб не дописывается.
- Под-файлы делятся по **интенту** (механика, сценарий), не по формальной структуре. Первая строка — `> Часть модуля [<module>](../<module>.md) — раздел найдёшь по индексу хаба.`
- Пороги `check-sizes.py`: хаб и под-файл — 44 000 байт; нерасслоённый док — 122 880 байт.
- Док — не хроника: в документ идёт устоявшееся знание, пересказ задачи — в историю.
- Расслоение — отдельным коммитом, после него полный `make flow-check`.

## Архивация истории модуля

Главный файл истории должен читаться одним `Read` (лимит — 25k токенов). Решение — двухуровневая структура:

```
flow/history/
├── <module>-history.md        ← главный файл: активные записи + однострочный архив
└── <module>-history/
    ├── 2026-Q4.md             ← полные записи периода + дайджест
    └── 2027-Q1.md
```

### Пороги и окно

- **Целевой размер главного файла — ~18k токенов, ~44 000 байт.** Оценка — `wc -c` / 2.42 (курс кириллического markdown). Не на глаз.
- **Окно активного периода** — подбирается так, чтобы после архивации главный файл был ≤ 18k токенов с запасом на 5–10 новых записей. Ориентиры: активный модуль — 3 месяца, средний — 6, редкий — без архива.
- Архивные записи группируются по календарным кварталам `YYYY-QN`.

### Компактный формат активных записей

Если даже активная часть в полном формате не влезает в целевой размер: N самых свежих записей модуля (адаптивный N ≤ 12) — полные, остальные активные — одной строкой `- YYYY-MM-DD — <заголовок записи>`. Решения с пометкой «намеренно» при свёртке не теряются — дописываются в строку: `- YYYY-MM-DD — <заголовок> — намеренно: <решение коротко>`. Применяется только при архивации. Данные не теряются: полная запись восстанавливается из git по заголовку.

### Дайджест периода

Полный дайджест — в шапке архивного файла, раздел `## Дайджест периода`:

```markdown
## Дайджест периода

**Правок за период**: N

**Топ-3-5 тем периода**:
1. <Название темы> (<кол-во> правок). <Опционально: технический паттерн>

**Горячие файлы**:
- `<путь>` — <кол-во> правок
```

В `## Архив` главного файла — одна строка на период, ссылка в заголовке:

```markdown
### 2026-Q4 (12 правок) — [полные записи](<module>-history/2026-Q4.md). Топ: <тема> (n); <тема> (n)
```

Темы — короткие осмысленные фразы («Безопасность симлинков», «Новые категории Xcode»), не «UI» и не «сервисы». Меньше 5 записей в периоде — темы не выделяются.

### Когда архивировать

- **Автотриггер** — `/dev:code` Шаг 9: после добавления записи главный файл превысил ~44 000 байт → в той же сессии режим АРХИВАЦИЯ из `/dev:history`. Срабатывание порога = разрешение; изменения истории — отдельным коммитом с `[skip-doc-check]`.
- **Ручной запуск** — `/dev:history <module>`.
- **Сигнал от субагента** — `context` не смог прочитать файл целиком и вернул `АРХИВАЦИЯ НАЗРЕЛА` → рекомендация в финальный отчёт. Посреди чужой задачи архивация не запускается.
- **Целостность:** записей до архивации = активные после + архивные. Проверяется счётчиком `grep -c '^#### '`.
