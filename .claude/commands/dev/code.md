# Workflow: code

Вся коммуникация ведётся только на русском языке.

Руководствуйся следующими правилами при работе над задачами в режиме `/dev:code`.

---

> **КРИТИЧЕСКОЕ ПРАВИЛО — читай первым.**
>
> 1. **Порядок.** Шаги выполняются строго по номерам. Не меняй их местами и не забегай вперёд: пока не закончен Шаг N, Шаг N+1 не начинается. Шаг пропускается только там, где это разрешено его же текстом (шаги 2, 7, 8).
> 2. **Один вопрос за раз.** Задал пользователю вопрос — на этом сообщение заканчивается: **остановись и жди ответа**. Не выполняй следующие шаги, не запускай субагентов, не задавай второй вопрос.
> 3. **План (Шаг 4)** всегда показывается пользователю и ждёт явного подтверждения — начинать реализацию до подтверждения плана запрещено, даже если задача кажется очевидной.
> 4. Остановка после интерпретации (Шаг 1) — условная, по «правилу остановки» в Шаге 1. Если вопрос задан — действует пункт 2.
> 5. **Безопасность удаления** (root-rule п.2) действует на всех шагах: удаление проверяется только тестами во временной папке, «Очистить» в реальном приложении не нажимается.

---

# Шаг 1. Сбор контекста и интерпретация

Базовый контекст:

1. `flow/rules/root-rule.md` — **уже загружен** через `AGENTS.md`. Перечитывай, только если его нет в контексте.
2. `flow/rules/glossary.md` — ищи в нём по правилу `root-rule.md`, «Before Work» п. 1.

Через глоссарий определи модуль и документы: найди слово — строка ведёт в основной документ (колонка «Куда идти»). **Нашёл строку — обязательно прочитай её основной документ**, прежде чем двигаться дальше: глоссарий — указатель, а не источник знаний. У расслоённого модуля (в доке — индекс под-файлов) открой и под-файл по теме задачи. Подгружай только то, что нужно для задачи. Если по глоссарию непонятно, где искать код — `flow/project-map.md`.

Просмотри недавние планы в `flow/plans/`, касающиеся этого модуля.

Отнесись к задаче критически: формулировка может предполагать неверное поведение macOS, невозможное без прав или опасное для данных пользователя. Мутная формулировка — попроси уточнение.

**Названные в задаче сущности проверь до плана.** Есть в тексте конкретное имя — тип, метод, папка, категория — грепни его:

- имени в коде нет → назови это и спроси, что имелось в виду; замену молча не подбирай;
- имя есть, но означает другое → покажи расхождение.

Расхождение выноси отдельной строкой в блок интерпретации; сошлось — молчи.

До подтверждения интерпретации разрешено читать только минимальный контекст: глоссарий, документацию модуля, точечные файлы кода, поиск по именам. Нельзя начинать реализацию, массовый поиск, планирование правок или изменение файлов.

Покажи интерпретацию запроса. **Не упоминай риски из истории модуля** — их анализ отдельный Шаг 3.

```text
Интерпретация запроса:

Текст: [как ты понял задачу]
Целевой результат (DoD): [что должно получиться]
Модуль: [scanning / cleanup / main-window / новый]
Затрагивает удаление: [да — что именно / нет]
```

**Правило остановки.** Если интерпретация добавляет к тексту задачи предположения, выбор между вариантами или расходится с его буквальной формулировкой — добавь вопрос «Всё верно? 1 — ✅ продолжай / 2 — ❌ нужно исправить» и **на этом остановись**. Если интерпретация тривиально совпадает с текстом задачи — вопрос не задавай, оставь блок как факт и продолжай в Шаг 2.

**Задача расширяет зону удаления** (новая категория, новый корень, ослабление `SafetyGuard`) — это всегда развилка: остановка обязательна.

Если пользователь уточняет запрос — скорректируй интерпретацию и покажи её снова.

# Шаг 2. Артефакты

Выполни шаг артефактов по инструкции `.claude/commands/dev/artifacts.md` (внутренний шаг, не отдельная пользовательская команда): краш-репорты, логи, скриншоты, листинги папок. Артефакты не нужны — шаг пропускается.

# Шаг 3. Контекст: история модуля

Самостоятельный шаг перед планом: подсветить риск сломать прошлые решения. Не сливай его с интерпретацией.

**Разрешения продолжать не спрашиваешь.** Находки идут в вывод сжато, решение по ним пользователь принимает вместе с планом. Исключение — одно, см. ниже.

Запусти субагента `context` (Agent tool, `subagent_type: context`), передай **имя модуля, суть задачи и предполагаемые файлы**. Нет файла истории модуля — шаг даёт «нет пересечений» без запуска субагента.

## Реакция на ответ субагента

- **`НЕТ ПЕРЕСЕЧЕНИЙ`** — одна строка-факт, без вопроса, сразу в Шаг 4:

```text
Шаг 3. История модуля <module> проверена (субагент) — релевантных пересечений нет.
```

- **`ПЕРЕСЕЧЕНИЯ:`** — выведи сжатую сводку и продолжай в Шаг 4 без вопроса. Не больше трёх самых релевантных находок, одна строка на находку:

```text
⚠️ Шаг 3. История модуля <module>: найдены пересечения

- <дата> — <заголовок записи> | <файл или область> | <риск одной фразой>
Горячий файл: <путь> — N правок

Учту в плане.
```

**Единственная остановка этого шага.** Субагент пометил находку `КОНФЛИКТ С РЕШЕНИЕМ` — оспариваемое поведение сделано **намеренно** прошлой задачей, а текущая задача его меняет:

```text
❌ Шаг 3. Конфликт с принятым решением

Задача просит: <что>
Но запись <дата> — <заголовок> сделала это намеренно: <цитата решения>

1 — ✅ Всё равно делаем (поясни, почему прошлое решение отменяется)
2 — ✅ Делаем опцией: прежнее поведение остаётся по умолчанию
3 — ❌ Останавливаемся
```

Показал блок — остановись и жди ответа.

Строка **`АРХИВАЦИЯ НАЗРЕЛА`** в ответе субагента — добавь в финальный отчёт рекомендацию `/dev:history <module>`.

Пользователь по ходу сказал, что находки нерелевантны — предложи запись в `flow/meta/feedback-log.md` для калибровки субагента.

# Шаг 4. План

```text
План работ:

[этап 1]
[этап 2]
[этап 3]

Риски из истории и как учтены: [по каждой находке Шага 3; пересечений не было — строку не выводи]

Начинаем выполнение?

1 — ✅ Всё верно, приступай
2 — ❌ Нет, нужно изменить
```

**Жди подтверждения пользователя.**

**Спутники по типу изменения** — проверь при составлении плана:

| Что меняешь | Что обязано попасть в план вместе с этим |
|---|---|
| Новый файл кода | положить в правильную папку внутри `Trash/` или `TrashTests/` — синхронизируемые папки, `project.pbxproj` не трогаем |
| Новая категория очистки | `case` в `CleanupCategory` со всеми свойствами; корни внутри `~`; тест `everyCategoryRootIsInsideHome` проходит; решение о выборе по умолчанию; строка глоссария |
| Любая правка удаления — `Cleaner`, `SafetyGuard`, корни категорий | тесты во временной папке: удаляется нужное **и** не удаляется лишнее |
| Новый путь, требующий прав (TCC) | обработка `isAccessDenied` и подсказка Full Disk Access |
| Видимая UI-правка | проверка в `make run` — скриншот, если среда позволяет; иначе — чеклист для ручной проверки пользователем |
| Настройки проекта, entitlements, Info.plist | правка build settings в `project.pbxproj` + `make build` |

Сохрани план в `flow/plans/<module>-<slug>.md`, если задача длиннее одного-двух этапов.

# Шаг 5. Реализация

1. Перед правками прочитай `flow/knowledge/engineering/code-style.md`.
2. Понадобился дополнительный контекст — расширяй минимально: один документ под одну оставшуюся неопределённость.

# Шаг 6. Проверка

1. Сверь результат с планом и DoD.
2. Прогони `make build`, затем `make test` — единые команды, строку `xcodebuild` вручную не собирай. Доказательство — код выхода 0 и `** TEST SUCCEEDED **`.
3. Упало **по сути** — исправь и повтори. Упало **по среде** (подпись, Xcode, симулятор) — не чини вслепую: покажи пользователю фактическую ошибку и попроси помочь с окружением.
4. **Ошибка сборки, причина которой не выводится из её текста** — после фикса пополни gotchas-документ `flow/knowledge/engineering/<слой>-gotchas.md` по `flow/meta/conventions.md` → «Правила для gotchas-документов». Нет файла — создай и зарегистрируй строкой в глоссарии.

# Шаг 7. Тесты

## Решение о тестах — принимаешь сам, без вопроса пользователю

Разрешения на тесты не спрашивай: реши по чеклисту, напиши — и сообщи факт в отчёте.

**Правка удаления — тесты обязательны всегда**, чеклист ниже для неё не применяется.

| Вопрос | Ответ «нет» — сигнал пропустить тесты |
|---|---|
| Есть ли в изменённом коде логика, вычисления, правила? | чисто UI-правки, лайаут, цвета — тесты не нужны |
| Можно ли тест запустить во временной папке, без реального `~`? | тест, зависящий от состояния диска пользователя, бесполезен и опасен |
| Проверяет ли тест реальное поведение, а не заготовленный ответ мока? | тест, подтверждающий стаб, ничего не даёт |
| Указывал бы провал на реальный баг, а не на окружение? | иначе тест создаёт шум |

**Два и больше «нет» — тесты не пиши**, причину назови одной строкой в отчёте.

Тесты оправданы — напиши их сам (1–5 сценариев) на Swift Testing. Единственный случай, когда спрашиваешь пользователя: тест требует новой инфраструктуры, которая больше самой правки.

Чеклист перед Шагом 8:

- [ ] Каждый тест содержит хотя бы один `#expect` / `#require`, который может реально упасть
- [ ] Файловые тесты работают в уникальной временной папке и убирают её в `defer`
- [ ] Ни один тест не трогает реальный `~` пользователя
- [ ] Тест упадёт, если намеренно сломать именно ту логику, которую он проверяет

Не выполнен пункт — исправь или удали тест. После — `make test`.

# Шаг 8. Code review

После тестов — **code review изменений** через субагента `code-reviewer` (Agent tool, `subagent_type: code-reviewer`; инструкция — `.claude/agents/code-reviewer.md`). Контекст проекта он грузит сам. Передай ему:

- суть задачи (1–2 предложения) и DoD;
- имя модуля;
- что ревьюить: незакоммиченное (`git diff`) или `git diff <база>`;
- путь к плану, если он есть;
- список документов знаний, которые ты уже читал.

Реакция:

- **High / Medium** — покажи пользователю, предложи поправить (вернись в Шаг 5) либо обоснуй, почему оставляем. После фиксов — `make test`.
- **Low / замечаний нет** — кратко в финальном отчёте.

**Когда шаг обязателен:** в диффе (`git diff --name-only`) есть `.swift`, `.pbxproj`, `.plist`, `.entitlements`, `.xcscheme` или `Makefile`. Пропуск разрешён, только если дифф **целиком** в `.md` — тогда одной строкой в отчёте.

# Шаг 9. Документация модуля и история

**Шаг обязателен — без него задача не закрыта.** Выполняется после тестов и ревью: документация пишется по финальному коду.

Цель — документация **актуальна и точна**. Устаревший абзац хуже отсутствующего: агент ему верит.

1. Через глоссарий локализуй документ затронутого модуля.
2. Сверь затронутую область с документом и определи состояние: **нет** / **неполна** / **актуальна**.
3. Действуй:
   - **нет** → создай `flow/knowledge/modules/<module>.md` по `flow/meta/conventions.md` → «Структура документа модуля», с обязательной `### Ключевые файлы`; правило в `flow/meta/code-to-module-map.json`; строка глоссария;
   - **неполна** → точечно дополни нужный раздел. Расслоённый модуль — пиши в под-файл по индексу хаба. Пиши устоявшееся знание, а не пересказ задачи;
   - **актуальна** → отметь в отчёте.
4. Новый ключевой файл модуля → строка в `### Ключевые файлы` и правило в карте `code-to-module-map.json`.
5. Новый термин → глоссарий, только имя: сущность, экран, категория, главный тип — словом в строку его документа. Методы и описания — в «Кодовые якоря» дока. Правила — `flow/meta/conventions.md` → «Правила для глоссария»; нарушение не пропустит `check-glossary` на Stop-хуке.
6. Изменился контракт безопасности удаления → обнови раздел «Контракт безопасности» в `cleanup.md`.
7. **Запись в историю — только если задача меняла код.** Добавь запись в `flow/history/<module>-history.md` сверху секции `## Активные записи` по `flow/meta/conventions.md` → «Формат записи истории модуля»:
   - заголовок `#### YYYY-MM-DD — <сообщение коммита>` — **дословно та же строка, что в Шаге 10**;
   - `Суть:` обязательно; `Решения:` — если задача приняла решение, которое выглядит как баг или ограничение, со словом «намеренно»;
   - нет файла истории — создай по шапке соседних файлов.

   После записи проверь размер: `wc -c flow/history/<module>-history.md`. Больше **44 000 байт** — выполни архивацию сам, в этой же сессии: режим АРХИВАЦИЯ из `.claude/commands/dev/history.md`. Срабатывание порога = разрешение. Изменения истории — **отдельным коммитом** с `[skip-doc-check]`, отчёт — отдельным блоком в Шаге 10.

# Шаг 10. Финальный отчёт

Отчёт — только то, что человек реально читает. Файлы не перечисляй, план и интерпретацию не пересказывай. Оформление — по `flow/rules/response-format.md`.

**Разделы, по которым сказать нечего, не выводи.** Это правило про вывод, а не про работу: шаги 7–9 обязательны по своим критериям.

1. **Суть**: что изменилось и почему — 2–4 предложения.
2. **Тесты**: какие добавлены и что проверяют — либо почему не добавлены.
3. **Ревью**: неисправленные замечания и почему. Всё закрыто — одной строкой.
4. **Документация и история**: одной строкой — что обновлено.
5. **Сообщение коммита** — одной строкой по [`flow/rules/naming-conventions.md`](../../../flow/rules/naming-conventions.md): завершённый результат, без тела, без упоминаний AI, дословно как заголовок записи истории.
6. **Риски / следующий шаг** — только если реально есть что сказать.
