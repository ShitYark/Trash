# Workflow: review

Вся коммуникация ведётся только на русском языке.

Руководствуйся следующими правилами при работе над задачами в режиме `/dev:review`.

---

> **КРИТИЧЕСКОЕ ПРАВИЛО — читай первым.**
>
> До показа интерпретации разрешён только минимальный контекст: `glossary.md`, список файлов, краткий `git diff --stat`, точечное чтение заголовков.
>
> До показа интерпретации (а при остановке — до подтверждения) запрещено проводить полноценное review, делать выводы о качестве или менять файлы.
>
> **Порядок и один вопрос за раз.** Шаги выполняются строго по номерам. Задал вопрос — сообщение на этом заканчивается.

---

# Шаг 1. Сбор контекста и интерпретация

Базовый контекст:

1. `flow/rules/root-rule.md` — **уже загружен** через `AGENTS.md`.
2. `flow/rules/glossary.md` — ищи по правилу `root-rule.md`, «Before Work» п. 1.

Через глоссарий локализуй модули затронутых изменений. **Нашёл строку — обязательно прочитай её основной документ.** Подгружай только то, что помогает проверить риски в изменённых местах.

```text
Интерпретация запроса:

Объект review: [коммит / diff / файлы]
Фокус review: [безопасность удаления, риски, регрессии, тесты, архитектура, стиль]
Scope: [что проверяется]
Точка входа через глоссарий: [термин / модуль / документ]
```

**Правило остановки.** Интерпретация добавляет предположения (сам выбрал объект или фокус) — добавь вопрос «Всё верно? 1 — ✅ продолжай / 2 — ❌ нужно исправить» и **остановись**. Тривиально совпадает — продолжай.

# Шаг 2. Артефакты

Выполни шаг артефактов по `.claude/commands/dev/artifacts.md`. Не нужны — шаг пропускается.

# Шаг 3. Проведение review

По умолчанию review выполняется без правок в коде. Приоритеты:

1. **Безопасность удаления** — любой путь к удалению в обход `Cleaner` + `SafetyGuard`, расширение разрешённых корней, ослабление нормализации путей, удаление без подтверждения, раскрытие симлинка цели
2. Баги, включая concurrency: диск на main actor, гонки, нарушения изоляции
3. Регрессии
4. Нарушения архитектуры: правило слоёв из `flow/project-map.md`
5. Недостающие тесты — особенно для правок удаления
6. Расхождения кода и документации модуля, включая «Контракт безопасности» в `cleanup.md`
7. Только потом стиль

Расхождения с документацией — отдельные findings категории «Документация модуля»: критичный контракт без описания → Medium/High, детали → Low.

Не расширяй scope дальше затронутых файлов и их зависимостей без основания. Review крупный — веди план в `flow/plans/`.

Самопроверка после каждого этапа:

1. **Не выдумывай факты** (root-rule п.12): у каждого finding есть `файл:строка` или фактический вывод команды.
2. **Интенциональность:** замечание про существующее поведение — сначала проверь, не сделано ли оно намеренно: `git log -S` / `git blame` сам, историю модуля — через субагента `context`. Вывод «так не задумано» без этой проверки не делай.

# Шаг 4. Формат результата

Findings, отсортированные по серьёзности. Для каждого:

1. Серьёзность: High / Medium / Low
2. Суть проблемы
3. **Файл и строка — обязательно.** Нет пруфа — либо иди проверь, либо выноси как гипотезу с пометкой «не проверено»
4. Почему это риск
5. Чего не хватает для уверенности

Замечаний нет — скажи явно и перечисли остаточные риски и пробелы проверки.

# Шаг 5. Ограничения

1. Код и документацию не правь, если пользователь отдельно не попросил. Исключение — план review в `flow/plans/`.
2. Нужны правки — предложи `/dev:code`.
3. Не хватает контекста — предложи `/dev:search`.

# Шаг 6. Финальный отчёт

Файлы не перечисляй — выводи только содержательные находки. Был создан или обновлён план — упомяни.
